# API conventions

## Base path and versioning

- Every business endpoint lives under `/api/v1/…`. A new major version (`/api/v2`) is introduced only for a breaking
  change; additive changes (new optional fields, new endpoints) stay in v1.
- Operational endpoints sit outside the versioned path: `/health/live`, `/health/ready`, and in Development only
  `/openapi/v1.json`.

## Resources

- Plural nouns: `/api/v1/households`, `/api/v1/instruments`.
- Nest only to express ownership: `/api/v1/households/{householdId}/members`. Never more than two levels.
- Identifiers are UUIDs (version 7, generated by the server). Clients never choose IDs.
- Actions that are not CRUD use a verb sub-resource on the owning resource:
  `POST /api/v1/sessions/{sessionId}/submit`.
- A search that carries free text is a `POST` with the text in the JSON body, never a query string, so the text never
  sits in a URL, a proxy or access log, or browser history: `POST /api/v1/support-resources/search` (D-93). Query
  strings carry filters and paging, never free text. A valid search answers 200 even when nothing matches
  (`outcome: no_match`).

## Methods and status codes

| Code | When |
| --- | --- |
| 200 | Successful read or update returning a body |
| 201 | Created; include a `Location` header |
| 204 | Success with no body |
| 400 | The request is malformed or fails validation (`ValidationProblemDetails`) |
| 401 | No valid token |
| 403 | Signed in but not allowed: the wrong role, or a required consent is missing (`sessions.participation_consent_required`). Another household's resource is 404, never 403 |
| 404 | The resource does not exist **or** the caller may not know it exists |
| 409 | The request conflicts with the current state (for example submitting an already submitted session) |
| 429 | A rate limit refused the request: `requests.rate_limited`, with `Retry-After` in seconds (D-79) |
| 500 | An unexpected server error |

422 is not used: validation failures are 400.

## Errors: ProblemDetails (RFC 9457)

Every error response is `application/problem+json` and carries a `traceId` that matches the server logs. The body never
contains exception messages, stack traces, SQL, host names or other internal detail.
A malformed JSON body returns MVC's generic message ("The input was not valid.") under its JSON path key; the parser's
own text (type names, line and byte positions) is not sent (`AllowInputFormatterExceptionMessages` is off).

Every ProblemDetails for an expected failure carries a `code` extension, a stable dotted code such as
`scoring.policy_not_approved` that clients translate. 400 validation responses (`ValidationProblemDetails`) carry
`errors` and no `code`. `ErrorResults` classifies every error code once: 400 (the request
is wrong), 403 (a required consent is missing), 404 (not found, or not the caller's to see), 409 (conflicts with the
current state), or 500 for codes that can only mean a server bug. A 500 carries no `code` and no detail.
`ErrorResultsTests` fails if a declared code is not classified.

A ProblemDetails on any status may carry the extension `safetyNotice` (D-138), beside `code` and `traceId`: the fixed value
`crisis_support` when a crisis detector fired on the participant's text, so a person who wrote a crisis message gets help even when
the request failed (the assistant's 502 and 503 and the support search's errors, for example). Clients show help for any string
value and never show server-provided text. The extension is absent otherwise, and it never depends on the database.

Media types: every error response, including 401 and 403, is declared and returned as `application/problem+json`, and
every success response is declared as `application/json`. No controller has a class-level `[Produces]`, because that
attribute rewrites every error to `application/json`. `OpenApiContractTests` asserts these media types for every
response in the contract.

Real 401 from the API:

```json
{"type":"https://tools.ietf.org/html/rfc9110#section-15.5.2","title":"Unauthorized","status":401,"traceId":"00-e85cad13aaaaa80ff4224eca53ecd9e1-412c64afe66bb62d-01"}
```

Unhandled exception (500), produced by `GlobalExceptionHandler`:

```json
{"type":"https://tools.ietf.org/html/rfc9110#section-15.6.1","title":"An unexpected error occurred.","status":500,"traceId":"00-…"}
```

A request the server cannot read (`BadHttpRequestException`, for example a body over the 64 KB limit of
`PUT /api/v1/sessions/{sessionId}/responses`) keeps the exception's status (413 there), with the status's standard
title, no detail and a trace ID. It is logged as a warning with the status only, never the exception's message.

Validation failure (400), produced by `ValidationFilter`; keys are camelCase property paths:

```json
{"type":"https://tools.ietf.org/html/rfc9110#section-15.5.1","title":"One or more validation errors occurred.","status":400,
 "errors":{"name":["'Name' must not be empty."],"age":["'Age' must be between 0 and 120. You entered 150."]},"traceId":"00-…"}
```

## Transport, headers and limits

- Deployed environments (anything but Development and Testing) accept HTTPS only: a plain-HTTP request gets 400
  `requests.https_required` and is not redirected; health probes are exempt. Responses carry HSTS (D-77).
- Every response carries `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`,
  `Referrer-Policy: no-referrer` and a `Content-Security-Policy` that loads nothing (D-78).
- Bodies are at most 1 MiB, headers 32 KiB and the request line 8 KiB; some endpoints set less (exports 16 KB,
  answers 64 KB). A bigger body answers 413.
- Every request passes a rate limit per token subject (or per address when anonymous); sensitive endpoints add a named
  policy (`[EnableRateLimiting]`). Every state-changing endpoint must name one; a test fails otherwise (D-79).

## Validation

- Every request body and query object has a FluentValidation validator next to its request record, registered in DI
  (`AddValidatorsFromAssembly` in `ApplicationServiceCollectionExtensions`).
- `ValidationFilter` runs the validator for every action argument before the action executes.
- Query-bound requests report camelCase keys too, for example `page` and `pageSize`. Binding errors (a value that is
  not a UUID, a date or a known enum, such as `?status=unknown`) also reach `ValidationFilter`
  (`SuppressModelStateInvalidFilter`), so they are camelCase as well. Never name a paging parameter `page`: MVC would
  treat the `page` query key as the model's prefix and ignore it.
- `PATCH` bodies are JSON merge patches (RFC 7396) read through `Optional<T>`: an absent property keeps the current
  value, and `null` clears a property that can be empty. A `null` for one that cannot is malformed (400 keyed at its
  JSON path).
- A request field that is a non-nullable value type, such as `effectiveFrom` on approve or `effectiveTo` on schedule-end
  and retire, must be present. A missing field returns 400 with its key; it never binds to the default value.
- The content-import body (`POST /api/v1/instruments/{instrumentId}/versions`) and the instrument-create body
  (`POST /api/v1/instruments`) are stricter still: every property must be present, including `isNonSubstantive` on
  each option and `ar` in each text (written as `null` while the Arabic is not known). See JSON below.
- Business-rule failures that depend on state (not on the shape of the request) return a domain `Error`, mapped by
  `ErrorResults` to 400, 403 (missing consent only), 404, 409 or 500, never thrown as exceptions.
- Clients validate every response body with Zod before using it.

## JSON

- camelCase property names; enums as snake-case strings (`in_progress`), in query strings too
  (`?status=in_progress`; an empty `?status=` means no filter, and numbers are refused there, though JSON bodies still
  accept them); `null` for absent optional values (no empty strings as "missing").
- Timestamps in ISO 8601 UTC with a `Z` suffix (`2026-10-11T09:30:00Z`). Dates without time use `YYYY-MM-DD`.
- Content JSON is read strictly with `ContentJson.Options`: the embedded content files, and over HTTP the content-import
  body (`POST /api/v1/instruments/{instrumentId}/versions`) and the instrument-create body (`POST /api/v1/instruments`),
  which `ContentJsonInputFormatter` reads ahead of MVC's own JSON formatter. Property names are case-sensitive; unknown,
  missing and duplicate properties, numbers in strings and enums sent as numbers are refused. Such a body returns 400
  `ValidationProblemDetails` keyed at the JSON path, for example `$.sections[0].items[0].options[0].value`, with the
  same generic message as any malformed JSON body (never the parser's text), and nothing is saved. Other request
  bodies keep MVC's JSON reading.
- Numbers as JSON numbers; money (if ever needed) as decimal strings with a currency code.

## Pagination

`GET` collections accept `?page=1&pageSize=20` and return the shape below. `page` is at least 1 and at most
`int.MaxValue / 100`; `pageSize` is 1 to 100. A value out of range returns 400 with the camelCase key.

```json
{ "items": [], "page": 1, "pageSize": 20, "totalCount": 0 }
```

## Idempotency

`POST /api/v1/sessions/{sessionId}/submit` and `POST /api/v1/admin/exports` require an `Idempotency-Key` header (a
client-generated UUID); a missing or malformed key returns 400 keyed `idempotencyKey`. A successful request stores the key for 24 hours in the same
transaction as the change, with the caller's subject, the operation, the resource ID and a SHA-256 hash of the request,
but no response body. A retry with the same key re-reads the resource and answers as the first request did. The same
key with a different request returns 409 `requests.idempotency_key_reused`. A failed request stores nothing, so it can
be retried with the same key. A request that finds the session already submitted (`already_submitted`) changes nothing
and stores no key either, so only the request that submitted is ever replayed as `submitted`. Expired keys are purged
hourly (D-54).

## Authorization

- Every endpoint requires a signed-in caller unless it carries `[AllowAnonymous]` (today: health endpoints and, in
  Development, the OpenAPI document).
- Policies (D-48, D-61, D-93): `Participant`, `HouseholdManager`, `AssignmentParticipant`, `SessionParticipant`,
  `Researcher`, `ExportRequester`, `ProgramAdministrator`, `SystemAdministrator`, `SupportCoordinator`,
  `PartnerReader`, `AnalyticsReader`, `QuestionnaireReader`, `SupportResourceReader`. Each needs a token subject and
  its roles; the OpenAPI document states each operation's policy. A new endpoint names a policy or is added to the
  exceptions in `DenyByDefaultTests` with a reason.
- Every refusal of a signed-in caller is audited (`authorization.resource.denied` or `authorization.role.denied`,
  D-81).
- Access to a household, member, assignment or session is decided by the server from the caller's identity and the
  platform's records (their household membership), never from IDs in the request. A failed resource check answers 404
  with the resource's not-found code, exactly as for an ID that does not exist, so IDs cannot be probed.
- No staff endpoint returns participants' answers; program administrators see progress and researchers see suppressed
  aggregates.

## OpenAPI

`Microsoft.AspNetCore.OpenApi` serves the document at `/openapi/v1.json` in Development only. Annotate actions with
`ProducesResponseType` so the document lists every status code.

The committed contract is `backend/openapi/v1.json`, and `OpenApiContractTests` fails when the API and the file differ.
The test host's `TestOnlyController` is excluded, and the snapshot is written without escaping `+`. After a deliberate
API change, regenerate it with `AZWAH_UPDATE_OPENAPI_SNAPSHOT=1 dotnet test --project FamilyResilience.IntegrationTests
--filter-class FamilyResilience.IntegrationTests.OpenApi.OpenApiContractTests` from `backend/`, review the diff and
commit it. Generated client types (planned) come from this
document; clients still validate responses at runtime.

## Health

| Endpoint | Checks | Response |
| --- | --- | --- |
| `GET /health/live` | Nothing beyond the process answering | `200 {"status":"Healthy"}` |
| `GET /health/ready` | Database reachable | `200 {"status":"Healthy"}` or `503 {"status":"Unhealthy"}` |

Only the overall status is returned; check names and errors stay in the server logs. Clients treat a 503 from
readiness as "connected, database not ready", not as a connection failure.
