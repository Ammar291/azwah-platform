# Database conventions

PostgreSQL 18.6 through EF Core 10 (Npgsql). Configurations live in
`backend/FamilyResilience.Infrastructure/Persistence/Configurations`, one per entity; model-wide rules live in
`Persistence/Conventions`. The domain model is described in [`domain-model.md`](domain-model.md).

## Naming

- Tables are snake_case plurals; columns are snake_case (`EFCore.NamingConventions`).
- Constraint prefixes: `pk_`, `fk_`, `ix_` (generated), and hand-named `ux_` (unique index), `ak_` (alternate key),
  `ck_` (check), `ex_` (exclusion), `trg_` (trigger). Named indexes need both the model name and
  `.HasDatabaseName(...)`, or the naming convention renames them.
- Bilingual text uses `<name>_ar` and `<name>_en` columns, mapped with `HasLocalizedText(x => x.Name, "name")`.

## Keys and relationships

- Every foreign key is `ON DELETE RESTRICT`. The only cascades are inside draft content (version → sections → items →
  options) and score result → contributions and category scores. A model test fails on any other cascade.
  A `DELETE` blocked by `ON DELETE RESTRICT` raises SQLSTATE `23001` (`restrict_violation`) with an `fk_…` constraint
  name; a child `INSERT` or `UPDATE` that breaks a foreign key raises `23503` (`foreign_key_violation`).
- **Foreign keys are indexed.** EF Core adds an index for each foreign key unless another index already starts with its
  columns, even a partial one that cannot serve every lookup. Such a key gets its own named index:
  `ix_assessment_assignments_family_member`, because `ux_assessment_assignments_live` starts with `family_member_id`
  but skips cancelled and expired assignments.
- **Long names are set by hand.** PostgreSQL cuts identifiers at 63 characters, so a generated name that would pass
  that limit is replaced: the four `support_referrals` foreign keys and their indexes are named
  `fk_/ix_support_referrals_session_member`, `_session_version`, `_rule_set_version` and `_consent_member`.
- **Composite foreign keys pin copied keys.** When a row copies a parent's key (a session copies its assignment's member
  and version; a response copies its session's version), it points at an alternate key on the parent that includes the
  copy, so the copies cannot disagree:

Section, item and option codes and display orders are also unique within their parent (`ux_instrument_sections_*`,
`ux_instrument_items_*`, `ux_response_options_*`); the domain stops duplicates first. `ConstraintErrorMap` turns the
indexes above into `Result` errors; any other unique violation becomes `persistence.conflict`.

To replace an approved version, either:

- **now:** retire the old version (`Retire(now, now)`) and approve the new one from the same instant inside one
  `ExecuteInTransactionAsync`, committing after each step, because the exclusion constraint is checked per statement; or
- **at a future time `T`:** call `ScheduleEnd(T)` on the old version and commit, then approve the new one from `T`. The
  old version stays Approved and effective until `T`; retire it with `Retire(T, now)` once `T` has passed.

`Retire` refuses an end later than now (`questionnaires.retire_in_future`).

To move the head or primary-earner flag from one member to another, use two commits inside one
`ExecuteInTransactionAsync`: clear the old member's flag and commit, then set the new member's flag and commit.
PostgreSQL checks the partial unique indexes row by row, and EF Core does not promise the order of the two updates
inside one save, so a single commit can fail with `households.head_already_exists` or
`households.primary_earner_already_exists`.

To score a session and refer it, also use two commits inside one `ExecuteInTransactionAsync`: record the score (which
moves the session to Scored) and commit, then read the referral consent with `GetActiveWithShareLockAsync`, add the
referral and commit. `trg_support_referrals_guarded` reads the session's status when the referral is inserted, and EF
Core does not promise that the session update comes first inside one save.

To approve a support resource whose code already has an approved version, `ApproveSupportResource` also uses two
commits inside one `ExecuteInTransactionAsync`: retire the approved version (with its audit event) and commit, then
approve the draft and commit. `ux_support_resources_one_approved_per_code` is checked per statement.

## CHECK constraints

Besides the generated enum checks: birth month 1–12 and birth year 1900 or later; the head has no relationship value;
version numbers, display orders and retry counts are positive or zero as appropriate; approved or retired versions,
rule sets and policies carry all approval columns; retired rows carry `retired_at`; effective windows end after they
start; waves close after they open; assignments expire after they are assigned and completed ones have
`completed_at`; a session's timestamps match its status; responses are modified no earlier than answered; consent is
withdrawn no earlier than granted; rule definitions are JSON objects; a referral's service, resolution code and
resolution time match its status (open has none, in progress has a service, resolved and cancelled have a resolution
code and time); an export job's attempts, row count, error code and times match its status
(`ck_export_jobs_status_shape`); a referral's hand-off columns are all set or all empty, and only once it has left
Open (`ck_support_referrals_hand_off_shape`); a partner names itself in Arabic and covers 1 to 20 categories; a
support resource has an `https` URL (`ck_support_resources_url_https`), 1 to 10 categories, at most 10 audiences, 1 to
5 service languages and a version number of 1 or more, carries Arabic text, the approval columns and a `review_due_at`
later than `approved_at` once approved or retired (`ck_support_resources_approval`), and has `retired_at` exactly when
retired (`ck_support_resources_retired`). The 366-day review cap is checked by the domain only. A safety alert (D-135) names a user or a household
(`ck_safety_alerts_subject`), has a household whenever it names a member (`ck_safety_alerts_member_household`), is High
exactly when its concern is `LowResilienceScore` (`ck_safety_alerts_severity_of_concern`), has language `en` or `ar` or
none (`ck_safety_alerts_language`), counts at least one occurrence with the latest detection no earlier than the first
(`ck_safety_alerts_occurrences`), and carries the acknowledgement and resolution columns its status requires
(`ck_safety_alerts_status_shape`).

## Triggers

Added by the hand-written migrations `AddDatabaseGuards`, `AddAssessmentEngineGuards`, `AddSupportReferralGuards`,
`AddPartnerHandOffGuards`, `AddAuditEventGuards`, `AddSupportResourceGuards` and `AddSafetyAlertGuards`.
Each raises SQLSTATE `23001` with a fixed message and no row data; the API turns it into a generic 500 because the
domain should have stopped the change first.

| Trigger | Rule |
| --- | --- |
| `trg_instrument_versions_immutable` | An approved version may only be retired (status, the end of an open window, `retired_at`, `updated_at`); retired versions and deletes of non-drafts are refused |
| `trg_instrument_content_immutable` | Sections, items and options change only while their version is a draft |
| `trg_rule_sets_immutable` | An approved rule set may only be retired |
| `trg_consent_policy_versions_immutable` | An approved policy may only be retired |
| `trg_assessment_responses_frozen` | Responses change only while their session is in progress; deletes are allowed when the transaction sets `azwah.erasure = 'on'` |
| `trg_assessment_sessions_guarded` | A new session copies its assignment's section; afterwards its assignment, member, version, section and `started_at` never change, `submitted_at` and `abandoned_at` are set once, `scored_at` is set once and moves only forward when a scored session is re-scored, and the status moves only from InProgress to Submitted or Abandoned and from Submitted to Scored (nothing leaves Abandoned) |
| `trg_audit_events_no_update` | Audit events are never updated |
| `trg_audit_events_no_delete`, `trg_audit_events_no_truncate` | Audit events are deleted only when the transaction sets `azwah.audit_retention = 'on'` (reserved for the approved retention job) and never truncated (added by `AddAuditEventGuards`, D-81) |
| `trg_score_results_no_update`, `trg_score_contributions_no_update`, `trg_score_category_scores_no_update` | Score results, contributions and category scores are never updated (added by `AddAssessmentEngineGuards`) |
| `trg_instrument_versions_bilingual_on_approval` | A version cannot move from Draft to Approved while any text of the version or its instrument lacks Arabic (added by `AddAssessmentEngineGuards`) |
| `trg_support_referrals_guarded` | A new referral is Open, its session is Scored, its rule set is an Approved referral rule set, and its consent is an active referral consent, read `FOR SHARE` so a concurrent withdrawal waits until the referral's transaction ends; afterwards its session, member, version, category, rule set, consent and `created_at` never change; a service is recorded only by the move from Open to InProgress, which re-reads the consent `FOR SHARE` and needs it still active, and never changes afterwards; the status moves only from Open to InProgress, Resolved or Cancelled and from InProgress to Resolved or Cancelled; a resolved or cancelled referral never changes at all; and deletes are allowed only when the transaction sets `azwah.erasure = 'on'` (added by `AddSupportReferralGuards`). `AddPartnerHandOffGuards` extends it: the partner, hand-off method, time and actor are set only by that same move and never change, and the partner must be active and cover the referral's category, read `FOR SHARE` |
| `trg_support_resources_immutable` | An approved support resource may change only its status (to Retired), `retired_at` and `updated_at`; a retired one never changes; deleting an approved or retired one is refused; drafts change and delete freely (added by `AddSupportResourceGuards`, D-92) |
| `trg_safety_alerts_guarded` | After insert, a safety alert's ID, user, household, member, source, concern, severity, first detection and session never change (the count, latest detection, status and who acknowledged or resolved it stay free), and deletes are allowed only when the transaction sets `azwah.erasure = 'on'`; both refusals raise `restrict_violation` (added by `AddSafetyAlertGuards`, D-135) |

The response and content triggers check both the old and the new parent on `UPDATE`, so a row cannot be moved into a
submitted session or an approved version. `azwah.erasure` is not a security boundary: any database role can set it, so
production must restrict who may delete responses and referrals through database permissions.

Triggers do not fire for everything: `TRUNCATE` skips row triggers, `SET session_replication_role = replica` disables
them, and the table owner (or a superuser) can disable or drop them. The production application role must therefore not
own the tables, must not hold `TRUNCATE`, and must not be a superuser.

Consequences: approved content is saved in two commits (draft content, then the approval); answering and submitting
a session are separate commits, and so are scoring a session and referring it, because EF Core does not promise
statement order inside one save.

## Generated columns and full-text search

`support_resources.search_vector` is the only generated column (D-93): a stored `tsvector` that PostgreSQL maintains
and EF Core never writes, mapped as the shadow property `SearchVector` with
`HasComputedColumnSql(SupportResourceSearchSql.VectorExpression, stored: true)` and indexed with GIN
(`ix_support_resources_search_vector`). English names, summaries and providers use configuration `english` at weights
A, B and C; the Arabic ones use `simple` after the Arabic normalisation (`SupportResourceSearchSql.NormaliseArabic`,
built from `translate` and `regexp_replace`, which are immutable). The one C# constant feeds the configuration and so
the migration; changing it changes the model and needs a new migration. The immutability trigger does not compare the
column, because it derives from the content columns.

The search itself is a read model (`SupportResourceSearch`): one constant statement whose term texts, configurations,
filters, time and limit are all parameters. `ix_support_resources_discoverable (review_due_at) WHERE status =
'Approved'` serves its filter. How terms are made: [`support-resource-discovery.md`](support-resource-discovery.md).

## Concurrency

Every aggregate root has a `Version` property mapped to PostgreSQL's `xmin` system column (`IsRowVersion()`, by
convention). Changing a child (a member, an item, a response) also updates the root's `updated_at`, so the root row
changes and `xmin` covers the whole aggregate. A stale update returns `persistence.concurrency_conflict`. Raw SQL that
returns an aggregate must select `xmin` explicitly: `SELECT t.*, t.xmin`.

Reading aggregates: repositories return child collections (sections, items, options, members, responses) in no
guaranteed order. Order by `DisplayOrder` (or another key) before displaying.

## Transactions

- One use case is one transaction: one `IUnitOfWork.CommitAsync`, or several inside one `ExecuteInTransactionAsync`.
  A failed result or an exception inside `ExecuteInTransactionAsync` rolls back everything, including changes already
  saved by `CommitAsync` inside it. After a failed commit, discard the scope.
- Domain events are cleared after each successful `CommitAsync`. If a later step makes the surrounding
  `ExecuteInTransactionAsync` roll back, those events (and their outbox rows) are gone with it, so discard the scope and
  do not reuse its tracked aggregates. No retrying execution strategy is enabled; enabling one would need the work
  inside `ExecuteInTransactionAsync` to be idempotent.
- Audit events for a change are staged with `IAuditLog.Stage` and commit with it. `RecordAsync` is for standalone
  events, such as recording a failed outcome after a rollback.
- Read-then-write rules across aggregates take a row lock: `IConsentRecordRepository.GetActiveWithShareLockAsync`
  (`FOR SHARE`) makes a concurrent withdrawal wait until the transaction ends. The referral trigger takes the same lock
  on the consent it inserts against, so a referral never commits against a consent withdrawn meanwhile. `IHouseholdRunLock` uses `FOR UPDATE` on
  the household row to serialise assignment runs (D-44) and roster confirmations (D-50); `ISessionLock` uses
  `FOR UPDATE` on the session row to serialise submissions (D-52) and saving answers against them, so answers sent
  during a submission get 409 `sessions.not_in_progress` rather than tripping the response trigger. Both must be called
  inside an open transaction.
- Submission commits three times inside one `ExecuteInTransactionAsync`: the submission (with its idempotency key), the
  score, then the routing decisions. The session's status trigger and the referral trigger each check the previous
  step, and EF Core does not order statements inside one save.
- No distributed transactions; nothing outside PostgreSQL takes part.

## Outbox

Every save writes the domain events of tracked aggregates to `outbox_messages` (type code, `jsonb` payload, occurred
at, status `Pending`) in the same transaction, and clears the events only when the save succeeds.

`OutboxProcessor` (D-56) claims one due message at a time with `SELECT … FOR UPDATE SKIP LOCKED`, only for types that
have a registered `IOutboxMessageHandler`, and runs the handler in its own scope. Success marks the row `Processed` with
`processed_at`. Failure increments `retry_count`, stores the short `last_error_code` `outbox.handler_failed` (never an
exception message) and sets `next_attempt_at` after an exponential backoff (2, 4, 8 … seconds, at most an hour); after
`Outbox:MaxAttempts` (5) the row is `Failed`. Handlers must be idempotent. The only handler is the export worker
(`analytics.export_requested.v1`, D-60); every other event stays `Pending`, referral events in particular because no
partner integration exists. The claim query
uses `ix_outbox_messages_pending_type_occurred_at (type, occurred_at) WHERE status = 'Pending'`, so Pending rows of
unhandled types and finished rows cost it nothing.

## Retention and deletion

- **Default:** deactivate, keep history, never cascade. Withdrawing a household or deactivating a member is a status
  change.
- **Periods** (open questions 12 and 22): none is approved. The retention job (`ApplyRetention`, D-88) does nothing
  unless `Retention:Enabled=true`, and each of `Retention:WithdrawnHouseholdDays`, `ProcessedOutboxDays` and
  `FinishedExportJobsDays` deletes nothing until it is set.
- **Erasure** (`IHouseholdErasure`, D-88) is one transaction that sets `SET LOCAL azwah.erasure = 'on'` and deletes in
  this order: safety alerts (about the household, its sessions or the accounts being erased; those accounts are first
  locked `FOR UPDATE`, so no alert or membership can be added for them meanwhile); support recommendations; referrals; score results (contributions and category scores cascade);
  responses; sessions; assignments; privacy requests; consent records; memberships; members; the household; platform
  users with no other membership and their role snapshots; then idempotency keys and outbox rows that name an erased
  ID. Audit events keep only opaque IDs. It refuses until `Erasure:ConsentRecords=delete` (open question 21). A new
  table that references a household or member must be added to `HouseholdErasure` in the right place, and
  `HouseholdErasureTests` must cover it.
- **Safety alerts** (D-135) keep no period: they stay until household erasure (open question 59, retention policy
  pending approval). An account is never kept for an alert's sake.
- **Database roles** (D-86): migrations run as the owner (`ConnectionStrings:Migrations` when set); the API runs as
  `azwah_app`, which `application-role.sql` grants DML on every table (default privileges cover new ones), INSERT and
  SELECT only on `audit_events`, and no DDL. Hand-written SQL that needs more than DML belongs in a migration.

## Privacy

The policy and the approvals it waits for are in [retention-policy.md](retention-policy.md).

- No names, identity numbers, contact details, region or free-text answers are stored. Identity-provider data stays in
  the token; only subjects (`granted_by`, `approved_by`, audit actor) are kept.
- Support-resource search text is never stored; its terms reach PostgreSQL only as query parameters (D-93).
  `support_resources` holds public directory content and no participant data.
- Neither IDs nor household references, nor any unkeyed or reversible hash of them, are treated as anonymous.
  Research exports use keyed pseudonyms whose key exists only in memory while one file is written (D-60); export
  files live outside the database, and `export_jobs` holds no rows of data.
- EF Core sensitive-data logging and Npgsql `Include Error Detail` stay off: PostgreSQL error details contain row
  values. Trigger messages contain no row data.

| --- | --- |
| Start PostgreSQL only | `npm run db:up` |
| Apply migrations | `npm run db:migrate` |
| Seed synthetic development data | `npm run db:seed` |
| Wipe the local database and start again | `npm run db:reset` |
| Run the persistence tests | `npm run api:test:persistence` (Docker running) |
| Create a migration | see `backend/README.md` |
